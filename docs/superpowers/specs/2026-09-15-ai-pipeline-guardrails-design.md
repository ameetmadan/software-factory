# AI Pipeline & Guardrails — Design

## Context

`software-factory` is a template/toolkit repo meant to jumpstart new project
ideas, covering the full lifecycle from requirements analysis through
one-click infrastructure-as-code deployment. That scope is too large for a
single design, so it's decomposed into six independent sub-projects:

1. **AI pipeline & guardrails** (this spec) — skills, conventions docs, and
   automation guardrails, portable across AI coding tools
2. Discovery/planning kit — requirements capture, feature scoping/prioritization, ADRs
3. Project scaffolding/generator — code templates for new projects, plus a
   future CLI generator
4. CI pipeline templates
5. IaC modules
6. Deployment automation

Each sub-project gets its own spec → plan → implementation cycle. This
document covers only sub-project 1, since it's the foundation every later
piece (and every project this factory eventually produces) will be built
and tracked with.

## Goals

- Ship working AI guardrails (skills + conventions) so future sub-project
  work — and any project later generated by this factory — starts with
  built-in tooling instead of a blank prompt.
- Make the conventions self-contained: the repo must work fully for anyone
  who clones it, without depending on the maintainer's global Claude Code
  configuration (global CLAUDE.md, pstack, superpowers).
- Track all planning and work as GitHub Issues, so state persists outside
  chat context.
- Keep the guardrails portable across AI coding tools (Claude Code, Cursor,
  and others that read `AGENTS.md`), not locked to one assistant.

## Non-goals

- No stack-specific scaffolding, CI templates, IaC modules, or deployment
  automation — those are sub-projects 3–6.
- No CLI generator yet — this repo stays a "use this template" GitHub
  template for now; a generator CLI is a later, separate sub-project.
- No requirements-analysis or feature-evaluation tooling — that's the
  discovery/planning kit (sub-project 2).

## Design

### 1. Docs layer

- `AGENTS.md` at repo root is the canonical, self-contained conventions
  doc: git workflow (conventional commits, branch naming, rebase-before-PR,
  squash-on-merge), security baseline, code quality standards, architecture
  patterns (hexagonal backend / atomic-design frontend, state management
  guidance), API design conventions, testing strategy (test pyramid),
  performance budgets, observability practices, and documentation
  standards. Content originates from the maintainer's global CLAUDE.md
  conventions but is copied in as project-local content — the repo must
  not depend on that global file being present.
- `CLAUDE.md` is a thin wrapper containing `@AGENTS.md`, so Claude Code
  loads the same content via its native import syntax.
- A short pointer file under `.cursor/rules/` notes that Cursor reads
  `AGENTS.md` natively; no duplicated content.

### 2. GitHub Issues as the roadmap/persistence layer

- Labels: one per factory piece (`discovery`, `scaffolding`, `ci`, `iac`,
  `deploy`, `ai-pipeline`), plus `epic` and `task` to distinguish
  roadmap-level items from concrete work.
- `.github/ISSUE_TEMPLATE/epic.yml` — one per factory piece, capturing
  scope, what's in/out, and links to its design doc once written.
- `.github/ISSUE_TEMPLATE/task.yml` — a concrete unit of work under an
  epic.
- `scripts/bootstrap-labels.sh` — uses `gh label create` to set up the
  label set in any repo created from this template (GitHub's "use this
  template" does not copy labels).
- The six-piece roadmap gets filed as epics in this repo immediately after
  this spec is approved, so tracking starts from day one.

### 3. Project-local skills (`.claude/skills/`)

- **`roadmap`** — creates/updates GitHub issues from conversation: new
  epic, new task under an epic, status updates. Keeps issues as the single
  source of truth instead of ad-hoc todos or chat-only state.
- **`new-subproject`** — kicks off the spec → plan cycle for the next
  factory piece. Pulls in the relevant roadmap epic, runs brainstorming
  questions scoped to that piece, writes the design doc, and files/links
  resulting tasks as GitHub issues.
- No stack-specific skills yet — those belong to the scaffolding, CI, and
  IaC sub-projects once they exist.

### 4. Guardrail automation

- Local pre-commit hooks via the `pre-commit` framework (language-agnostic):
  - commit-message linting for conventional commits
  - secret scanning (gitleaks) before every commit
- `.github/workflows/ci.yml` — backstop on PRs, since local hooks can be
  bypassed with `--no-verify`:
  - re-runs commit-lint and secret-scan checks server-side
  - a placeholder **test** job that no-ops for now (no app code exists
    yet), wired so later sub-projects can drop real test commands in
- Branch protection (required status checks on `main`) is a GitHub repo
  setting, not something expressible in code — documented in the README
  as a one-time manual setup step.

### 5. Repo structure

```
software-factory/
├── AGENTS.md
├── CLAUDE.md                    # @AGENTS.md
├── .cursor/rules/                # pointer note re: AGENTS.md
├── README.md                     # what this is, the 6-piece roadmap, how to use it
├── .claude/skills/
│   ├── roadmap/
│   └── new-subproject/
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── epic.yml
│   │   └── task.yml
│   └── workflows/ci.yml
├── .pre-commit-config.yaml
└── scripts/bootstrap-labels.sh
```

### Validation

No app code exists to unit-test — this is tooling, so it's validated
behaviorally:

- `CLAUDE.md`'s `@AGENTS.md` import resolves correctly in a fresh Claude
  Code session.
- `pre-commit` rejects a bad commit message and a planted fake secret, and
  accepts a clean commit.
- The CI workflow runs the same checks against a test PR.
- `scripts/bootstrap-labels.sh` creates the full label set (run for real
  against this repo, since it needs the labels anyway).
- The `roadmap` skill can file a real issue; the `new-subproject` skill can
  walk through kicking off sub-project 2 or 3.
